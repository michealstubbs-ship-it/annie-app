Add a cross-customer signal pool: share genuinely-discovered BD signals across overlapping-profile accounts, cut discovery cost, and seed new signups faster

Michael's idea: "if one customer has the same market choices as another,
our brain/back ops is able to realise that, and share the same data
between multiple consultants... maybe this could also save credits? This
could also potentially help with first day sign ups."

This extends a pattern already live in this codebase at two other levels —
company_enrichment/company_contacts (an objective company fact, once
discovered, is reused by every account researching that company) and
annie_learned_sources (which companies/sources are worth checking for a
sector/market, grown by every account's own scan) — up one more level, to
the actual signal EVENT itself: the funding round, the leadership
appointment, the live job posting.

WHAT'S SHARED, WHAT ISN'T: only the discovered FACT and Annie's own
factual/analytical reasoning about it (why it matters, the candidate
angle, the peer-company positioning, who to approach, the candidate
profile) is pooled. introMessage is NEVER pooled — it explicitly names one
specific recruiter's own firm ("their firm is called X") and can't be
reused for a different one. A small, new, no-web-search Anthropic call
(personalizePoolHits in scanShared.js) regenerates introMessage fresh, and
re-voices the rest in the new recruiter's own tone/writing style, for
every consumer of a pooled fact. Discovery is shared; interpretation
isn't.

HOW MATCHING WORKS: a pool entry carries the discovering customer's own
sector/location/function selections as hints (not Apollo's own free-text
industry classification, which uses a different taxonomy and would be an
unreliable match key). A later, different customer's own scan only
consumes a pool entry if their profile has real overlap: at least one
shared sector AND one shared location, plus (for a live_job entry
specifically, since a job posting's relevance is tied to a function in a
way a company-wide funding/leadership signal isn't) at least one shared
function.

WHERE THIS IS WIRED IN (both scan entry points, scanShared.js has the
actual shared logic):
- scan-now-background.js, round 1 — this is also literally a brand new
  account's first-ever scan, so the "help with first day sign ups" ask and
  the cost-saving ask turn out to be the exact same code path. Before
  running the expensive parallel sector-group discovery, check the pool
  for fresh, overlapping, not-already-seen matches. A full pool hit (covers
  this account's whole feed target on its own) skips the parallel sector-
  group Anthropic web-search calls ENTIRELY for this round — this account's
  first dashboard populates in the time it takes one cheap, few-seconds,
  no-search personalization call to run, instead of however long several
  parallel 90-120s web-search calls take. A partial or empty pool match
  falls straight through to exactly the same discovery this file has
  always run, with any partial pool hits merged in afterwards as a free
  bonus signal — never a reason any account gets LESS than it would have
  gotten today.
- intelligence-scan.js, the recurring 12-hourly cron — same shape, scaled
  to this file's smaller per-run signal cap (5): a full pool hit skips this
  customer's one Anthropic call for this run, a partial hit merges in
  alongside the normal single discovery call, unchanged.

Every genuinely fresh discovery (not itself sourced from the pool) gets
written through to the pool after enrichment, via a new signal_pool table
(migration: supabase-migrations/2026-08-27-signal-pool.sql, applied to
both staging and production already) — same RLS shape as
company_enrichment/company_contacts (service-role writes only, readable by
any authenticated customer). First discoverer wins on a duplicate — the
fact doesn't change based on who found it second.

New tests: netlify/functions/lib/scanShared.test.js covers
writeToSignalPool (row shape, never includes intro_message, logs rather
than throws on a write failure), fetchSignalPoolMatches (sector+location
overlap required, function overlap additionally required for live_job
only, excludes a dedup_key the customer already has, respects the
requested limit, logs rather than throws on a read failure), and
personalizePoolHits (maps AI output back onto each hit by index, falls
back to the pool's own original facts for anything the AI call leaves out,
returns an empty array — never throws — on any failure, which is what
makes the whole mechanism fail safe back to today's exact behavior).

IMPORTANT — what this does NOT change for any account with no pool
overlap yet (the common case until enough overlapping accounts exist):
byte-for-byte identical to today. The pool check runs, finds nothing, and
every existing code path executes exactly as it always has. This is
additive, not a replacement of the existing discovery pipeline.

Also found and fixed two real bugs while answering "do you see any gaps,"
not just a size question:

1. getLearnedSources used to order by first_seen_at ASCENDING — so once a
   sector's list filled its cap, the OLDEST-ever-discovered entries
   permanently occupied every slot, and brand new discoveries (exactly the
   "Annie getting smarter over time" this whole table exists for) could
   never surface in a prompt again once that ceiling was hit, no matter how
   current or relevant they were. Now orders by last_confirmed_at
   DESCENDING — the most recently reconfirmed-active entries win the
   available slots, so stale entries age out first instead of new ones
   being locked out.

2. That fix only works if last_confirmed_at actually means something.
   recordLearnedDiscoveries (Annie's own AI-discovered rows) was upserting

   frozen at whatever the very first insert set it to, forever. Only the
   separate customer-CRM-add trigger (learn_company_for_sectors) was ever
   correctly bumping that timestamp. Now a real upsert (ON CONFLICT DO
   UPDATE) that stamps last_confirmed_at fresh on every write, matching the
   SQL trigger's own behavior — first_seen_at is deliberately left out of
   the upserted columns, so a repeat write still never loses when something
   was originally discovered, only refreshes "still active."

No migration needed — last_confirmed_at already exists on both environments

EIGHTH FOLLOW-ON, same thread (2026-08-27), Michael: "What else should we

Five SECURITY DEFINER functions had never had their default Postgres
grants locked down, unlike every admin RPC this session has already
hardened the same way. Postgres auto-grants EXECUTE to PUBLIC on every new
function, and PostgREST auto-exposes every public-schema function as a
callable REST RPC — regardless of whether it was ever meant to be called
that way. Four of these five (learn_company_for_sectors,
learn_from_customer_company, learn_from_customer_candidate,
record_signal_pool_outcome) exist purely to be invoked by their own AFTER
INSERT triggers — confirmed via grep across the whole codebase, zero
direct .rpc(...) callers anywhere. Left as-is, this meant a fully
unauthenticated visitor could call learn_company_for_sectors directly —
POST /rest/v1/rpc/learn_company_for_sectors with any onboarding user's uuid
— and write straight into the SHARED annie_learned_sources table,
completely bypassing RLS via SECURITY DEFINER, no login required. The
exact table this whole session has spent so much effort keeping clean.

Fixed with the same REVOKE/GRANT pattern already used for the admin RPCs:
revoked EXECUTE on all four from public/anon/authenticated entirely (no
legitimate caller needs it — Postgres invokes a trigger function directly
as part of statement execution, which isn't an EXECUTE-checked call path,
so this doesn't touch normal operation at all). A fifth function,
my_active_team_ids(), is different — team_members' own live RLS policy
genuinely calls it as authenticated, so only anon's grant was removed,
authenticated's was revoked-then-explicitly-re-granted.

Separately, the same advisor pass flagged three usage-cap reservation
functions (apollo_reserve_credits, anthropic_reserve_tokens,
theirstack_reserve_credits — real, legitimately server-called functions,
no RPC-exposure issue) missing SET search_path, unlike every other
SECURITY DEFINER function in this schema. Re-created with identical
bodies, only that clause added — closes a search_path-injection hardening
gap with no behaviour change.
