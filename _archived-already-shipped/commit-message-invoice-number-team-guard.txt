Security fix, found during tonight's "what else should we check" pass over production (get_advisors + direct pg_proc inspection), not from the earlier QA exercise.

next_invoice_number(p_team_id uuid) is SECURITY DEFINER, granted to `authenticated`, and had no internal check that the caller actually belongs to p_team_id -- unlike every one of the 13 other advisor-flagged SECURITY DEFINER functions in this codebase, which all correctly guard on profiles.is_admin (confirmed by reading pg_proc.prosrc for each one directly). Its only real caller, send-invoice.js, always reaches it with a team_id read via RLS from the caller's own invoices row, so normal product use was never exposed -- but the RPC itself is directly callable via PostgREST (/rest/v1/rpc/next_invoice_number) by any signed-in user with an arbitrary team_id, independent of that RLS-scoped context. Not a data leak, but a real integrity gap: any customer could have burned or advanced another team's invoice sequence.

Fix mirrors the same pattern every sibling admin RPC already uses (RAISE EXCEPTION on a failed guard check) -- here the check is "auth.uid() has an active team_members row for p_team_id" instead of is_admin, since this isn't an admin-only function, it's a per-team one. This is the exact membership check already used elsewhere in this codebase (the invoicing_details RLS policy itself, and getCustomerWatchlistCompanies in scanShared.js).

Already applied directly to both staging (tqzafepeicfybxqysjjx) and production (tsnthomwislodczhshpt) via migration, and verified live on both: a same-team call passes the new guard (confirmed on staging, which fails afterwards only on a separate pre-existing staging/prod schema difference -- invoicing_details doesn't exist on staging -- unrelated to this fix); a cross-team call is correctly rejected with "Not authorized" on production itself, confirmed without mutating any real customer's invoice counter (the guard raises before the row is ever touched). This file is being committed purely so the change has a proper migration record in git -- there is nothing left to deploy, the database already has this live.
